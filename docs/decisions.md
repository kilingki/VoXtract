# 결정 기록

## 채택한 초기 구성

| 선택 | 근거 | 대안과 현재 기각 사유 |
| --- | --- | --- |
| Python 3.12+ / FastAPI | Python 서비스와 연동 용이, 요청 검증·API 명세를 점진 추가 가능 | stdlib HTTP는 향후 업로드·검증 직접 구성 필요. Flask도 가능하나 API 중심 흐름에 FastAPI 선택. Django는 규모가 큼 |
| Uvicorn 한 프로세스 | 앱과 향후 단일 실행기를 함께 관리 | 다중 worker·별도 큐 서비스는 동시성·운영 부담 증가 |
| 표준 HTML/CSS/JavaScript | 파일 선택·fetch·반응형 UI를 빌드 없이 구성, PWA 확장 가능 | React/Vue/Vite는 현재 UI에 추가 빌드·의존성 관리 필요. 화면 상태 복잡화 시 재평가 |
| 같은 출처의 UI/API | 서버·포트 하나, CORS 설정 불필요 | 별도 프런트엔드 서버 불필요 |
| uv / pyproject.toml / uv.lock | 기존 WSL에 uv 사용 가능, 의존성 잠금으로 재현성 관리 | pip+venv도 가능하나 별도 핀 생성 절차 필요. Poetry는 추가 도구 부담 |
| unittest와 실제 HTTP 검사 | 추가 테스트 패키지 없이 실행 골격 검증 | pytest/httpx는 실제 필요가 생길 때 평가 |
| 파일 기반 작업 (설계) | 단일 사용자·순차 처리에 DB 운영 불필요 | SQLite는 조회·동시성 요구 증가 시 검토. Redis/Celery는 현재 과도함 |
| 상태 폴링 우선 (설계) | 긴 작업 상태 조회와 재접속에 단순함 | WebSocket/SSE는 실시간 전송 필요 시 검토 |
| 입력 취득·오디오 준비와 추론 분리 (설계) | 녹음·동영상·YouTube를 같은 ASR→FA 흐름으로 확장 | 출처별 추론 파이프라인 복제는 중복·복구 정책 불일치 발생 |
| ASR별 어댑터와 내부 전사 형식 (설계) | 초기 Qwen 이후 다른 런타임을 작업별 선택 가능 | Qwen 응답 직접 사용은 교체 비용 증가. 실제 두 번째 계약 전 범용 플러그인 체계는 과도함 |

FastAPI 실행·정적 제공은 [공식 서버 실행](https://fastapi.tiangolo.com/deployment/manually/)과 [정적 파일 문서](https://fastapi.tiangolo.com/tutorial/static-files/)를 참고했다. 의존성 범위는 의도 없는 주요 버전 변경을 줄이기 위한 초기 선택이며 실제 설치 버전은 uv.lock이 기준이다.

## 1단계 조사 결과와 정책 결정

2026-11-21: 외부 계약의 출처·버전·로컬 설정·확인 수준은 [연동 계약 기록](integration-contracts.md)에 모았다. 아래 기술 방향은 확인한 계약에 따른 설계이며 기능 구현은 아직 없다.

| 기술 방향 | 근거·적용 범위 |
| --- | --- |
| canonical WAV를 한 번 준비하고 ASR·FA에 동일 bytes 사용 | 청크 sample 범위를 보존하려면 16 kHz·모노·signed 16-bit PCM이 필요. 입력 준비를 별도 단계로 둠 |
| ffprobe·ffmpeg를 외부 실행 도구로 사용 예정 | 갤럭시 M4A를 ASR 청크 계약에 맞게 준비할 필요가 확인됨. 2단계에서 입력 검사, 3단계에서 준비 실행을 구현·검증. Python 패키지를 지금 추가하지 않음 |
| ASR raw JSON 보존, FA 정렬 전 text 수정 금지 | 현재 FA는 ASR의 audio·chunks를 소비. UI·작업 조정은 어댑터가 변환한 내부 결과 사용 |
| FA 시간은 canonical 파일 시작 기준의 초 | 외부 응답이 offset을 이미 적용. 겹침 병합은 앱 책임이며 3단계에서 규칙·테스트 확정 |
| 불명 외부 실행은 자동 재전송하지 않음 | 공개 작업 조회·멱등·강제 취소 계약 없음. 재시작 후 다른 추론도 보류하고 운영자 idle 확인·명시적 해제 필요 |

### 확정: 입력 길이와 분할 처리 방향

2026-11-21 사용자 피드백: 입력 오디오 길이 상한은 **2시간(7,200초)**으로 잡는다. 길이 상한과 별도로 처리 단위의 threshold를 두고, 긴 입력은 여러 부분으로 나눠 처리하는 방향을 채택한다. 30분은 사용자가 제시한 threshold 예시이며 기본값 확정이나 실측된 최적값으로 취급하지 않는다. 파일과 향후 YouTube 입력에 같은 오디오 준비·분할 경로를 사용하되 YouTube 취득 구현은 확장 B로 유지한다.

threshold 후보가 30분이면 `N=ceil(전체 길이/threshold)`개의 대략 같은 길이 구간을 만드는 것을 추천한다. 40분은 20분×2, 65분은 약 21분 40초×3, 120분은 30분×4다. 구체적 sample 경계·경계 문맥·시간 복원·재개 설계는 [아키텍처](architecture.md#긴-입력의-분할-처리-설계안)를 기준으로 하며 아직 구현하지 않았다.

### 확정: 초기 입력·저장·내보내기

2026-11-21 사용자 결정: 원본 파일 크기와 앱 저장 총용량의 고정 상한은 두지 않고, 나머지 제안은 채택한다. 디스크 여유 1 GiB 확보는 저장 총량 quota와 구분해 유지한다. 아래 정책으로 2단계 구현을 시작할 수 있다. 처리 threshold의 최종값과 잡음 제거 도입 여부는 3단계 품질 검증에서 다루며 2단계의 선행 조건이 아니다.

| 항목 | 채택 정책 | 이유·후속 검증 |
| --- | --- | --- |
| 초기 형식 | 오디오 전용 M4A(AAC)·WAV. 컨테이너·코덱·오디오 stream을 probe하고 허용 조합만 접수 | 갤럭시 녹음 사용 사례를 지원하되 임의 동영상·코덱은 확장 A로 유지. 실제 갤럭시 샘플 필요 |
| 파일 바이트 제한 | VoXtract에서 원본 파일당 고정 바이트 상한을 두지 않음. 기존 200 MiB 제안 폐기 | 스트리밍 저장으로 메모리에 전체를 적재하지 않음. 실제 오디오 길이 0초 초과·2시간 이하, 형식·코덱 검증, 디스크 여유 검사는 유지. 외부 추론 multipart 한도와 구분 |
| 언어 | 한국어 우선, ASR 요청 `language=ko`; 모델 선택 UI는 후속 확장 | 조사한 설정·FA의 ko→Korean 지원과 일치. 혼합 언어 품질은 실제 샘플 확인 |
| 보존 | 원본·canonical·raw ASR/FA·최종 결과·실패 자료를 수동 삭제 전까지 보관. 기간에 따른 자동 삭제 없음 | 재시도·품질 검토 근거 보존. 디스크 여유가 부족해지면 기존 자료를 지우지 않고 신규 접수 또는 해당 쓰기를 거절 |
| 용량 | data/ 총용량 상한 없음. 기존 10 GiB 제안 폐기. 디스크 여유 1 GiB 이상 유지 | 접수·준비·결과 쓰기에서 실제 filesystem 여유와 다른 작업의 예약을 확인. 다음 쓰기로 여유 기준을 침범하면 중단. ENOSPC 시에도 원자적 접수/완료를 확정하지 않음 |
| 수동 삭제 | 대기·완료·외부 종료가 확인된 실패 작업 삭제 지원. 실행 중·외부 실행 불명 작업은 삭제 거절 | 실행기·재시도와 충돌하지 않게 잠금 사용. 삭제 후 원본·파생 파일·메타데이터까지 제거하고 재시작 후 중간 삭제를 복구 |
| 임시 청소 | 접수 실패·업로드 중단은 가능한 즉시 정리. 재시작 시 활성 참조 없는 미확정 임시 자료만 정리 | 확정 작업 자료·외부 실행 불명 자료를 임시 자료로 오인해 삭제하지 않음. 실행 중인 다른 인스턴스가 없음을 먼저 확인 |
| 추론 재시도 | 자동 재시도 0회. 사용자 명시 재시도, 외부 종료 확인 후 허용 | HTTP 단절이 모델 종료를 뜻하지 않음. 같은 유효 ASR 결과가 있으면 FA부터 재개 |
| 내보내기 | UTF-8 TXT·버전 있는 JSON. 초기 SRT/VTT 제외 | ASR의 근사 segment 시간을 정확한 자막으로 오인하지 않게 함. JSON은 내부 결과 기준, raw 외부 JSON은 일반 결과 API로 노출하지 않음 |

용량 예약은 앱 총량 quota 대신 실제 디스크 여유에서 1 GiB와 다른 접수·처리의 미사용 예약분을 뺀 가용 공간을 기준으로 한다. 원본 길이가 알려지지 않은 업로드도 다음 블록을 쓰기 전 여유를 확인하며 Content-Length를 신뢰해 검증을 생략하지 않는다. canonical·분할 파생 파일·결과의 예상 추가 쓰기를 계산하고 실제 쓰기에서도 여유와 ENOSPC를 처리한다. 30분 canonical PCM의 오디오 본문은 57,600,000 bytes, 2시간은 230,400,000 bytes(약219.7 MiB)다. WAV header와 분할 문맥의 추가 공간은 별도다. 디코딩이 비정상적으로 길어지거나 2시간 길이 제한을 초과하면 중단하고 부분 결과를 공개하지 않는다. 정확히 2시간인 유효 입력은 허용한다. 실행 도구의 구체적 timeout·결과 크기 상한·예약 구현은 각 기능 단계에서 확정하고 검사한다.

## 남은 계약·구현 결정

- 기존 로컬 배포에서의 실제 E2E 확인 범위는 [로드맵](roadmap.md#3단계-진행-상태)을 따른다. 다른 배포의 버전·접속 주소·인증·설정은 별도로 확인한다.
- 실제 갤럭시 M4A의 접수는 2단계에서 확인했다. canonical과 원본 재생의 동기는 확인이 필요하다. 추가 오디오·동영상의 트랙 선택·지원 포맷은 확장 범위다.
- 처리 threshold는 30분 후보로 유지하고 3단계에서 최종값·경계 처리 규칙을 검증한다. 잡음 제거는 기본 ASR 결과 평가 후 필요할 때 비교 실험하는 방향으로 검토하며 현재 별도 모델은 추가하지 않는다.
- YouTube 취득 도구와 허용 링크 범위, 호스트·리디렉션 검증, 취득 제한 및 준비 단계 상태·복구 정책.
- 두 번째 ASR의 실제 계약과 InferSwap 연동, 공통 전사 스키마, 지원 언어·FA 호환성, 선택 UI와 설정·버전 기록 형식.
- 내부 결과 스키마 v1과 정렬 병합 초기 규칙은 3단계에서 구현했다. 모바일에 표시할 단위와 내보내기 형식의 세부 필드는 4단계에서 확인한다.
- 외부 실행 불명 해제와 단계 재개는 모의 API에서 검사했다. 실제 런타임 종료 확인과 추론 timeout·응답 크기 상한의 운영 적정성은 미검증이다. [구현 기준](architecture.md#3단계-순차-실행)
- Tailscale HTTPS와 Windows/WSL 연결 경로, 대상 모바일 브라우저 버전, PWA 설치·캐시 세부 정책.

새 결정은 실제 계약이나 검증 근거와 함께 이 문서를 갱신한다. 중요한 미결정 사항은 구현 편의를 위해 추정하여 고정하지 않는다.
